# Как участвовать в разработке kacho-corelib

Спасибо за интерес к проекту. Этот документ описывает, как сообщить о проблеме,
подготовить изменение и провести его через ревью. `kacho-corelib` — библиотека
общих пакетов платформы Kachō; изменения здесь затрагивают все сервисы-потребители,
поэтому к совместимости и тестам требования строгие.

## Сообщить об ошибке или предложить улучшение

Все задачи ведутся в **GitHub Issues**:
`https://github.com/PRO-Robotech/kacho-corelib/issues`.

- **Баг** — приложите версию, шаги воспроизведения, ожидаемое и фактическое
  поведение, релевантные логи. Метка `bug`.
- **Улучшение / фича** — опишите задачу и зачем она нужна, до обсуждения дизайна.
  Метка `enhancement`.
- Перед заведением проверьте, нет ли уже похожего issue.

Об уязвимостях сообщайте приватно (GitHub Security Advisories), не через публичные Issues.

## Окружение

- Go 1.25+, Postgres 16+, Docker (для integration-тестов на testcontainers).

```bash
make test     # go test ./... -race -cover (integration требует Docker)
make lint     # golangci-lint
```

## Поток изменения

1. Заведите (или возьмите) issue и опишите в нем, что собираетесь делать.
2. Отведите ветку от актуального состояния основной ветки.
3. Внесите изменение **вместе с тестами** (см. ниже).
4. Откройте Pull Request: в описании — что и зачем, ссылка на issue
   (`Closes #<n>`), как проверяли.
5. Пройдите ревью; CI (build, vet, lint, govulncheck, тесты) должен быть зеленым.

Сообщения коммитов — в формате **Conventional Commits**
(`feat:` / `fix:` / `docs:` / `refactor:` / `test:` / `chore:` / `ci:`).

## Стандарты кода

- **Только горизонтальное.** Сюда выносится то, что нужно 2+ сервисам. Доменная
  бизнес-логика остается в репозитории сервиса. Пакеты узкие и направлены внутрь
  (зависят от stdlib и инфраструктурных библиотек, не друг от друга без нужды).
- **Без ORM.** Доступ к БД — handwritten pgx.
- **Secure-by-default.** TLS/mTLS-хелперы fail-closed при включении; авторизация
  fail-closed при недоступности PDP; identity принимается только с доверенной границы.
- **Совместимость.** Экспортируемый API потребляется всеми сервисами — ломающие
  изменения сигнатур согласовываются и проходят по всем потребителям.
- **Ошибки** — стабильный контракт: корректные gRPC-коды и фиксированные тексты,
  без утечки внутренних деталей БД наружу.
- **Каждый файл** с исходным кодом, схемой, конфигом или скриптом начинается с
  хедера лицензии:

  ```
  Copyright (c) PRO-Robotech
  SPDX-License-Identifier: BUSL-1.1
  ```

- **Комментарии** объясняют, какую задачу решает код и как он работает, — кратко и
  по делу; форматирование — `gofmt`.

## Тесты

Изменение не принимается без тестов в том же PR:

- **unit** — чистая логика пакета через моки/фейки (`*_test.go`); таблично, детерминированно.
- **integration** — для SQL/конкурентных инвариантов: testcontainers Postgres, включая
  конкурентные сценарии для CAS/UNIQUE/SKIP-LOCKED (`*integration_test.go`).

Тестируйте поведение, а не реализацию. Тесты, проверяющие отсутствие уже удаленного
поведения, в кодовой базе не держим.
